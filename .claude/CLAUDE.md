## 2. 編集〜本番反映の流れ（この順番を必ず守る）

| 手順 | あなたがやること | 担当者に聞くこと |
|---|---|---|
| 1️⃣ 聞く | 何を・どこを・どう変えたいかを聞く。曖昧なら**画面のどこか**（ページ名・見出し）を聞き返す | 「◯◯ページの△△の部分で合っていますか？」 |
| 2️⃣ 探す | 該当ファイルを探す。**同じ内容が書いてある所を全部探す**（下の「探す場所」） | 「同じ記載が◯か所あります。全部変えますか？」 |
| 3️⃣ 説明 | 「今こうなっている → 直すとこうなる」を文章で見せる。仕組みのファイル（§3）を変える必要がある時は、この OK をもらった後に、続けてもう1問として聞く | 「この内容で進めてよいですか？」 |
| 4️⃣ 直す | **OK をもらってから**ファイルを編集する（§3 を守る） | — |
| 5️⃣ 自分で点検 | **担当者に見せる前に、自分で確かめる**（§4）。①`python3 check_site.py` ②見た目が変わる修正は `python3 check_site.py --shots ページ名` で画像を撮り、**自分で画像を見る**。❌は直す | （⚠️があれば）「念のため確認させてください。◯◯の根拠になる資料はありますか？」 |
| 6️⃣ 見てもらう | このパソコンの中の確認用の画面を出し、担当者に**内容が希望どおりか**を見てもらう（§4） | 「◯◯ページの△△の所を見てください。希望どおりなら『OK』と言ってください」 |
| 7️⃣ 反映の確認 | 何が・いつ・誰に見えるかを伝える | 「本番に反映すると、**約1〜10分後に**ホームページを見た全員に表示されます。反映してよいですか？」 |
| 8️⃣ 反映 | 下の「反映のコマンドの順番」のとおり | — |
| 9️⃣ 本番で確認 | 数分待ってから本番のページを取得し（`curl -s https://www.kireisia.co.jp/ページ名`）、変更が入っているか自分で確かめる。担当者には**スマホで見てもらう** | 「本番に反映されました。スマホで◯◯ページを開いて、△△の所を見てください。おかしければすぐ教えてください（すぐ元に戻せます）」 |

- 🔴 **7️⃣の「反映してよいですか？」に OK をもらう前に `git push` しない。**
- 🔴 担当者が OK を出すまで、次の修正に進まない。
- 1回の反映には1つの依頼だけ入れる（何かあった時に戻しやすくするため）。
- スマホでの確認は、**反映した後でしかできない**（確認用の画面はこのパソコンの中でしか開けない）。だから 5️⃣ の画像での点検を省かない。画像を撮れなかった時は、9️⃣ のスマホ確認を「必ず・すぐ」お願いし、崩れていたらすぐ戻す（§5）。

### 探す場所（同じ内容は何か所にも書いてある）
電話番号・料金・営業時間・住所・サービス名・写真は、次の全部を検索する（言葉を変えて2回以上。例：`9,000`・`9000`・`９，０００`／`20:00`・`20時`）：

| 場所 | 注意 |
|---|---|
| 各ページの本文（`*.html`） | 一番下のフッターは全ページに同じ物がある |
| 各ページの頭の説明文（`meta description`・`og:`・`twitter:`） | 画面には出ないが、検索結果や SNS に出る |
| 検索エンジン向けの見えない情報（`<script type="application/ld+json">`） | 料金・営業時間・電話が入っている |
| `content/` の中の JSON | 🔴 **同じ値が HTML と JSON の両方にある所は、両方直す**（表示の時に JSON の値で上書きされる。片方だけだと食い違う） |
| ブログの原稿（`content/blog/*.md`） | 過去の記事の値まで変えるかは、担当者に聞く |
| `build_blog.py` の中 | ブログ一覧・ブログ記事の**上のメニューと一番下のフッター**はここに書いてある（§3 の例外） |
| `llms.txt` | AI 検索向けの案内 |

- 探さない・直さない：**一番上の階層の** `blog/` フォルダ・`blog.html`・`sitemap.xml`（自動で作り直される）／`_backup` で始まる控えのファイル・フォルダ
  - 🔴 `content/blog/`（ブログの原稿）は**探す**。検索から `blog` という名前のフォルダをまとめて外すと、原稿まで外れて見落とす
- **同じ数字でも別の商品のことがある**（例：お掃除機能付きエアコンと窓用エアコンが同じ金額）。一括で置き換えず、前後の文を1件ずつ読んで仕分ける
- **画像の中の文字**（キャンペーンの画像に書かれた料金など）は検索では見つからない。料金・電話・営業時間を変える時は、関係しそうな画像を開いて見る。見つけたら「画像の中にも書いてあります。画像の作り直しが必要です」と担当者に伝える（文字だけ直して画像と食い違う状態を黙って作らない）
- 他社も含めた相場の数字（「8,000〜12,000円が目安」等）は、自社の料金とは別。勝手に変えない

### 反映のコマンドの順番
1. `git fetch` で、作業中に他の変更（編集画面での保存・制作担当の修正）が入っていないか見る（ここで何も無くても、4 の時に入ってくることがある。4 の結果を必ず見る）
2. **変えたファイルだけ** `git add` する（`git add .`・`git add -A` は使わない）
3. `git commit`（日本語で、何を変えたか分かるように。例：「トップページの電話番号を変更」）
4. `git pull --rebase`（commit の前に実行すると「変更が残っている」と断られる。必ず commit の後）
5. 🔴 **4 で新しい変更が入ってきたら、反映の前に**：①`python3 check_site.py` をやり直す ②入ってきた変更の中に、今回直した内容と同じ物（例：新しいページのフッターの営業時間）が無いか**探し直す** ③見つけたら、黙って直さず担当者に伝えて OK をもらう ④入ってきた変更に `build_blog.py`・`content/blog/` が含まれていたら、`python3 build_blog.py` をもう一度実行する
6. `git push`（直前に自動点検が走る。**止められたら無理に通さない**。`--no-verify` は使わない。出た ❌ を直す）
   - 自動点検は「このフォルダの中身」と「実際に反映される中身」が同じかも見る。**使う画像を登録し忘れている・直したのに記録していない・使わないファイル（縮小前の元画像など）がフォルダに残っている**と ❌ で止まる。縮小前の元画像は、最初からこのフォルダの外に置いて作業する
- push が断られたら、4 からやり直す。2回続けてダメなら、止まって担当者に説明する。

### ブログ・フッターを変えた時の作り直し
- `content/blog/`・`content/blog-categories/`・`build_blog.py` のどれかを変えたら、**`python3 build_blog.py` を実行**し、作り直された `blog/`・`blog.html`・`sitemap.xml`・`llms.txt` も**同じ反映に含める**（`build_blog.py` だけを変えた時は、自動処理は動かない）。
- 実行すると `sitemap.xml` の主要ページの日付が今日になる。これは正常。
- 作り直したら `git status` を見る。**今回の依頼と関係ない記事まで変わっていたら**（他の人の変更がまだ作り直されていなかった等）、そのことを担当者に一言伝えてから反映する。

## 3. 🔴 守るルール（例外なし）

### 内容のルール（法律・信用に関わる）
- **お客様の声・口コミ・評価点・件数・実績の数字を作らない**（景品表示法違反になる）。担当者が実物（アンケートの集計・実際の口コミの文面とお客様の了解）を渡した物だけ載せる。「だいたいそのくらい」は根拠にならない。
- 「業界No.1」「地域最安」「満足度◯％」等は、**根拠の資料が無ければ載せない**。担当者に頼まれても載せない。代わりに「事実として約束できること」を聞いて、それを書く提案をする。
- **地名（大阪市・城東区・東成区・中央区・東大阪市など）を、文章の中に何度も入れない**。対応エリアの欄に1回まとめる（入れすぎると不自然で、検索でも逆効果）。
- 料金の相場を書く時は**関西の相場**だけ。根拠がない相場は書かない。
- 前からページにある表現（「人気No.1」「口コミ評価」等）は、今回の依頼に関係なければ触らない。担当者に聞かれたら「根拠の資料が手元にあるか確認をおすすめします」と答える。
- 人が写っている写真を載せる時は、**写っている人の了解があるか**を担当者に聞く。

### 写真・画像を入れる時
1. **もらった画像を自分で開いて見る**。依頼の内容と合っているか確かめる（「スタッフの写真」なのに人が写っていない、等は進める前に聞く）。
2. **縮小してから入れる**：長辺 1600px 以下・**1枚 500KB 以下**（これを超えると自動点検が止める）。
   - Mac：`sips -Z 1600 元の画像 --out 新しい画像`
   - それ以外・失敗した時：Python の Pillow が入っていれば使う。入っていなければ、担当者にパソコンの写真アプリの「サイズ変更」で小さくしてもらう（手順を1歩ずつ案内する）
3. ファイル名は**半角の英小文字・数字・ハイフン**（日本語・空白は使わない）。置き場所は `images/`。
4. 今ある画像の役割をそのまま引き継ぐ時は、**同じ名前で上書き**し、その画像を使っている全部の所で `?v=数字` を1つ上げる（上げないと古い画像が表示され続ける）。
5. 画像の説明（`alt`）を、新しい画像の中身に合わせて直す。`width`・`height` が書いてある所は、新しい画像の縦横に合わせる。縦横の比率が変わる時は、見え方が変わることを 3️⃣ で担当者に伝える。

### 作業のルール（サイトを壊さないため）
- `git push --force`、`git reset --hard`、履歴の書き換え（amend・rebase -i）は**絶対にしない**。
- ファイルの削除は、担当者に「何が消えるか・戻せるか」を説明して OK をもらってから。
- 🔴 **下の「触ってはいけない所」のファイルを「消して」「いらなさそう」と言われたら、消さない。** 何のためのファイルかを説明し、残すことをすすめる。それでも消したいと言われたら、消すと何が起きるかをもう一度具体的に伝える（`CNAME`・自動点検・この編集ルールは、頼まれても消さない）。
- 前からあった不具合で点検が ❌ になった時は、黙って直さない。「今回の変更とは別に、前からの不備が1つ見つかりました。直さないと反映できないので、一緒に直してよいですか？」と伝え、OK をもらって**今回の変更と一緒に**直す（説明文に両方書く）。自分の変更が原因でない ❌ が何度も出る時は、`check_site.py` の該当する点検を読んで原因を調べる。点検の方が誤っていると分かったら、§7 の手順で点検を直す。

### 仕組みのファイル（気軽に触らない。変える時は §7 の手順）
変える前に必ず担当者へ「何が変わるか」を説明して OK をもらう。OK の後、`python3 check_site.py --confirm-protected ファイル名` で記録する（記録しないと自動点検が反映を止める。記録の後にもう一度変えたら、確認し直し。**このコマンドでは英語の確認画面が出る**ので、先に担当者へ伝える。担当者の OK なしに記録しない）。記録した後の点検に出る「⚠️ 確認済みとして記録されています」は、聞き直さなくてよい。

| ファイル | 理由 |
|---|---|
| `CNAME` | 1文字でも変えると**ホームページが表示されなくなる**（何があっても変えない・消さない） |
| `.pages.yml` | 編集画面（Pages CMS）の設定。壊すと編集画面が開けなくなる |
| `.github/` の中 | 自動処理の設定。壊すとブログ・サービスの自動更新が止まる |
| `build_blog.py`・`build_services_menu.py`・`js/services-order.js` | 自動処理・表示の仕組み本体 |
| `check_site.py`・`.githooks/`・`.claude/` の中 | 反映前の自動点検と、この編集ルール。弱めたり外したりしない |
| `robots.txt` | 検索エンジン向けの設定。変えると検索に出なくなることがある |
| `.gitattributes` | Windows でも自動点検が動くようにする設定 |
| `googleed253135e72c7780.html` | Google Search Console の所有確認。消すと Search Console が使えなくなる |
| `content/` の中のファイルの**形**（項目名・並び） | 編集画面と表示の両方が壊れる。**中身の文字を変えるだけなら OK**（記録も不要） |

- `build_blog.py` で変えてよいのは2つだけ：①ページを足す時に `MAIN_PAGES` へ1行足す（`.claude/page-guide.md`）②ブログの上のメニュー・一番下のフッターに書いてある**文字**（営業時間・電話・住所・ページ名）を直す。どちらも担当者の OK と記録が要る。

### 直接編集しても消える所（自動で作り直されるため）
- `blog/` の中・`blog.html`・`sitemap.xml` → 元（`content/blog/` のマークダウン・`build_blog.py`）を直して作り直す
- `llms.txt` の「ブログ記事一覧（自動更新）」〜「ブログ記事一覧ここまで」の間（それ以外の部分は手で直してよい）
- `content/extra-services-index.json`

## 4. 点検と、見てもらい方

### 自分で点検する（担当者に見せる前）
| コマンド | 何が分かるか |
|---|---|
| `python3 check_site.py` | リンク切れ・画像なし・データの壊れ・`CNAME` の変更・ページの頭の設定の抜け・sitemap の入れ忘れ・大きすぎる画像・鍵らしい文字列・今回足した文の中の「根拠の確認が要る表現」・仕組みのファイルの変更。**❌＝直すまで反映しない／⚠️＝担当者に確かめる** |
| `python3 check_site.py --shots ページ名.html`（複数並べてよい） | スマホ幅（390px・320px）と PC幅（1280px）の画像を撮り、**横はみ出しを数字で測る**。出てきた画像ファイルを自分で開いて見る（右側の灰色は枠の外。白い部分がページ）。Chrome か Edge を使う |

- **不具合の相談を受けた時も、最初に `python3 check_site.py` を走らせる**（壊れている所の手がかりになる）。
- 画像を見る時に確かめること：横はみ出し（数字で出る）・文字の重なり・切れ・メニューの崩れ・画像の縦横比。これは**あなたの仕事**で、担当者には頼まない。
- 画像にはページの一番上から一番下まで写る。ただし**ボタンを押して出る小窓の中（サービスの「詳細」の価格表など）は写らない**。そこを直した時は、文字（HTML と `content/` の JSON）で確かめ、6️⃣ で担当者に「◯◯の『詳細』を押して、価格表を見てください」と開いて見てもらう。
- 見た目が変わらない修正（検索エンジン向けの見えない情報だけ等）は、画像と 6️⃣ を省いてよい。担当者には「見た目は変わりません」と伝える。
- 画像を撮れなかった時（Chrome も Edge も無い・`[S004]` が出る）：その旨を担当者に伝え、6️⃣ でパソコンの画面を見てもらい、**反映した直後にスマホで必ず見てもらう**。崩れていたらすぐ戻す（§5）。

### 担当者に見てもらう（確認用の画面）
ファイルを直接開く（`file://`）とデータが読めず、表示が崩れて見えます。必ず小さな表示用サーバーを使う：

1. 空いている番号を使って起動する：`python3 -m http.server --bind 127.0.0.1 8781`（このフォルダで実行。使われていたら番号を変える。`--bind 127.0.0.1` は必ず付ける＝同じ Wi-Fi の他の人から見えないようにする）
2. `http://localhost:8781/変えたページ.html` を開いてもらう（URL をそのまま貼る）
3. 見てもらうのは**内容が希望どおりか**だけ。「◯◯ページの△△の所」と、見る場所を具体的に伝える（幅を変える・エラー表示を見る等は頼まない）
4. 確認が終わったらサーバーを止める

## 5. 元に戻す時・困った時

### 「元に戻して」と言われた時・反映後におかしくなった時
1. `python3 check_site.py` を走らせて、壊れている所を確かめる
2. `git log`（日時つき）で最近の変更を見る。**「（via Pages CMS）」＝編集画面での保存／「自動更新」＝自動処理**。どの変更の話かを、日時と内容で担当者に確かめる（「◯月◯日◯時の『△△』という変更で合っていますか？」）
3. 戻すと何が消えるかを伝えて OK をもらう（「キャンペーンの帯も一緒に消えます」）
4. `git revert --no-edit <そのコミット>` で戻す（その変更だけを取り消す。履歴は残るので安全。説明文が英語まじりになるのは構わない）
5. 点検 → 「反映してよいですか？」→ 反映 → 本番で確認（§2 の 5️⃣〜9️⃣ と同じ）
6. 担当者には「◯◯を取り消して、△△の前の状態に戻しました」と伝える

### 困った時
| 状況 | やること |
|---|---|
| 本番が表示されない（全ページ） | ①`python3 check_site.py` で `CNAME` などを確かめる ②`git log` で直近の変更を見て、心当たりがあれば担当者の OK をもらって取り消す ③それでも直らなければ「大事なこと」（§7）として制作担当へ連絡 |
| 編集画面（Pages CMS）が開けない | `.pages.yml` を最近変えていないか確認。変えていたら取り消しを提案 |
| 反映（push）でログインを求められる・断られる | §1「GitHub へのログイン」 |
| 何をしたらいいか分からない依頼 | 推測で進めない。担当者に聞き返す |
| ドメイン・お問い合わせフォーム・Google の設定について聞かれた | `.claude/site-info.md` に書いてある事実だけ答える。書いていないことは推測で答えず「このフォルダの情報では分かりません」と伝え、そのサービスの管理画面のどこを見れば分かるかを案内する |

- まず自分で調べて解決する。制作担当に連絡するのは §7 の「大事なこと」だけ。

### 仕組みのファイルを変える時の手順（§3 の表のファイル）
新しい機能を足す・自動処理を直す・自動点検の誤りを直す、などで必要になった時は、次の順で行う。

1. **本当に仕組みを変える必要があるか**を先に確かめる（文字や画像の変更で済むなら、仕組みは触らない）
2. 担当者に「なぜ必要か・何が変わるか・うまくいかなかった時はすぐ戻せること」を説明して OK をもらう
3. 変える**前**に自動テストを流し、通ることを確かめる：`python3 -m pytest tests -q`
   （pytest が無ければ、その環境に合った方法で入れる。`node`・`yaml` が無い環境では一部が「skipped」になるが、それは正常）
4. 小さく変える（1回の反映に、仕組みの変更は1つだけ）
5. 変えた**後**にもう一度 `python3 -m pytest tests -q` と `python3 check_site.py` を流す。テストが落ちたら、**テストの方を書き換えて通さない**（落ちた理由が「仕様を変えたから」の時だけ、担当者に説明してからテストを直す）
6. `python3 check_site.py --confirm-protected ファイル名` で記録 → §2 の流れで反映 → 本番で確認
7. 反映の後に、関係する動きを実際に確かめる（例：`.pages.yml` を変えたら、担当者に編集画面を開いてもらう。自動処理を変えたら、数分後に `git log origin/main` で自動の更新が入ったか見る）。おかしければ、すぐ取り消す（§5）

- `CNAME` は変えない（変えるのは、ホームページの住所そのものを変える時だけ＝「大事なこと」の 2）。
- 自動点検（`check_site.py`）が**正しい変更を誤って止めている**と分かった時は、点検を飛ばさず、上の手順で点検の方を直す。直す前に、なぜ誤りと言えるのかを担当者に説明する。
